# ContentMachine Video Collector: решение v1 (исследование, 21.10.2026)

**Статус:** проектная архитектура; ни одного платного Apify-запуска
не выполнено, адаптер не реализован и не развёрнут. Это отдельный
модуль получения *кандидатов*, не конкурент RTB и не система аналитики.

## Зачем он нужен

RTB генерирует утверждённую человеком иерархию
`direction -> branch -> research_hypothesis`; SRE принимает видео и
определяет его релевантность фактам/категориям. Между ними нужен
**Video Collector** для получения реальных видео с происхождением и
разрешениями. Без него можно использовать ручной импорт URL/CSV D1,
но ни объёмных исследований, ни статистической проверки таксономии
невозможно честно обещать.

Действующий `intelligence.discovery` — PostgreSQL D1 ingest:
URL/CSV, нормализация, provenance, дедупликация, отслеживание
запусков, очередь, аудит и UI. Это **не внешний поиск**.
Существующие downloader'ы TikTok/Instagram/YouTube — отдельные
инструменты для явно выбранных пользователем ссылок, а не
массовые поисковые адаптеры.

## Проверенные варианты входных данных

### A: Apify Clockworks TikTok Scraper (первая кандидатная интеграция)

- Actor: https://apify.com/clockworks/tiktok-scraper
- Input: https://apify.com/clockworks/tiktok-scraper/input-schema
- Output: https://apify.com/clockworks/tiktok-scraper/output-schema
- API: https://docs.apify.com/api/v2
- `searchQueries`, `resultsPerPage`, `searchSection='/video'`,
  `videoSearchSorting` (например `MOST_RELEVANT`),
  `postURLs`, `profiles` и `hashtags` — публичные входы.
- Результаты содержат по крайней мере ID, caption, время публикации,
  автора и доступные показатели (проверять null; разные акторы
  предоставляют разные поля).
- Публичная карточка показывает тариф **от $1.70 / 1000 результатов**
  на момент исследования; это НЕ фиксированная полная стоимость:
  тариф плана, фильтры/сортировка, вычисления/дополнительные
  события, успешность и ненужные данные влияют на итог.
  Публикуемые поставщиком цены проверить в консоли перед оплатой.
- Для 10 000 **поставленных актором результатов** базовая арифметика
  при таком тарифе = $17, но это **не** прогноз стоимости
  10 000 подходящих уникальных свежих роликов.
- Публичные контракты не раскрывают приватный scraping-транспорт
  коммерческого Actor; на его стабильность без теста не полагаться.

**Корректное исполнение:** серверный POST
`/v2/actors/clockworks~tiktok-scraper/runs` с токеном в
Authorization header. Получить `runId`, дождаться
статуса через GET `/v2/actor-runs/:runId`, затем получить
`defaultDatasetId` и читать
`/v2/datasets/:datasetId/items?offset=N&limit=K`.
Хранить внешние run и dataset ID для восстановления после сбоя.
Синхронный 300s вызов подходит лишь коротким тестам и может
оборваться на сетевом ожидании; длительный collector должен
быть асинхронным.

Важно: права на использование и хранение выводить из
договора с поставщиком и условий TikTok, а не из наличия
JSON/URL. При недостаточных разрешениях — заблокировать
импорт, медиа и derived metrics.

### B: собственные open-source сборщики (не основа v1)

Далее можно тестировать:
- https://github.com/omkarcloud/tiktok-scraper
- https://github.com/davidteather/TikTok-Api
- https://github.com/Evil0ctal/Douyin_TikTok_Download_API

У них доступен исходный код, но стабильность, условия доступа,
требования cookie и легальность конкретного способа получения
данных нужно отдельно изучить. Не предлагать обход защит
платформ и не использовать скрытые авторизационные данные.

### C: официальный TikTok Research API (не коммерческий путь v1)

https://developers.tiktok.com/products/research-api/
https://developers.tiktok.com/docs/en/research-api-faq

TikTok явно исключает рекламодателей/коммерческих пользователей
из Research Tools; нужны критерии независимого некоммерческого
исследования и разрешение конкретного проекта. Не строить
коммерческий ContentMachine на предположении о доступе к
Research API. Даже при законном доступе видео статистика
из Research API может запаздывать, поэтому это не
надёжная гарантия оперативных Breakout Scores.

## Минимальная архитектура Video Collector v1

`Approved Taxonomy v1` -> `Query Planner` ->
`Actor Adapter/CSV Import` -> `Provider Raw Run IDs` ->
`Validate + Rights + Normalize` -> `Deduplicate` ->
`Store in existing Discovery D1` -> `SRE Classification` ->
`Unmatched Queue + Human Review` -> `Analytics C & Features A/B`.

### Идемпотентность / данные

Коллектор не должен создавать второй независимый каталог:
`videos` — один canonical identity, `discoveries` — отдельные
события получения, `sources/source_policy_versions` — договорные
права, `search_runs` — история запусков, `jobs` — фоновые
задания. Новые сущности при необходимости:
- `collector_plans`: project, approved taxonomy version,
  node IDs, список запросов, пользовательские ограничения,
  источник/actor, version.
- `collector_attempts`: внешний run_id, dataset_id,
  request_hash, spending consent, budget reserve,
  status, ошибки, pagination checkpoints, фактические расходы.
- `collector_links`: canonical video_id -> source discovery
  -> taxonomy node hypothesis, плюс SRE score/unmatched outcome.
- `collector_metric_snapshots`: только если можно хранить
  и выводить сравнимые views/likes/comments/observed_at/source
  на основе явных разрешений.
- Все извлечённые показатели nullable. Не подменять
  неизвестное на `0`; не принимать опубликованность или
  просмотры без provenance.

Ускоритель: повторно использовать
`intelligence.discovery.normalize`, `discovery.service`,
`jobs`, миграции PostgreSQL и проектный UI. Не создавать
вторую систему Discovery ради простого адаптера.

### Подтверждения и расходы

- Пользователь выбирает проект, платформу, направления,
  поисковые запросы, лимит результатов и бюджет.
- Отдельное подтверждение точной операции поставщика;
  `search` в UI до подтверждения — только preview, НЕ вызов.
- Для asynchronous Actor вычитывать уже запущенный
  `runId`, а не запускать новый POST после таймаута;
  неизвестная цена/исход -> `uncertain` до reconciliation.
- Ограничения количества запросов, времени, paginated reads,
  429 backoff, право отменить дальнейший сбор.
- Интерпретировать ограничения видео/аккаунтов/временных
  периодов согласно публичному контракту provider Actor
  и записывать inputs/versions.
- Платные аккаунты/токены: хранить только локально вне Git,
  никогда не передавать в URL query или run logs.
- Без explicit media rights **не скачивать** ролики,
  не извлекать скрытые персональные данные, не запускать
  мультимодальную обработку.

### Масштабирование и проверка результатов

**Эксперимент до масштабирования:**
1. Выбрать 1 гипотезу RTB, 2-3 понятных запроса, платформу TikTok.
2. На предварительном 20-50 результатов вручную проверить:
   правильные identity, timestamp, provenance, повторы,
   доступность ключевых полей и однозначность цены.
3. Сравнить реальные результаты с RTB:
   precision@20 по Human Review, сколько SRE пометил uncertain,
   recall proxy по вручную размеченным позитивным запросам,
   доля недоступных/повторяющихся результатов.
4. Только после согласования текущей полной стоимости,
   retention, прав и проверки качества расширять до
   сотен/тысяч. 10 000/мес — это KPI **qualified, fresh, unique**,
   не просто запрошенные у Actor строки.

## Что остаётся согласовать до реализации

- Доступен ли пользователю Apify, какое у него право на
  коммерческую аналитику собранного, какая актуальная
  схема Actor и полный effective unit price.
- Нужен сначала TikTok-only MVP или одновременно YouTube
  Shorts/Instagram (рекомендация: TikTok-only).
- Нужно ли на MVP получать только metadata+URL или
  дополнительно captions; медиа отдельно при правах.
- Максимум spend на один запуск и на месяц, политика
  расписания, условия удаления/истечения прав.
- Тестовая выборка и критерии качества до
  подключения SRE и Performance C.

реконструкции Actor помечено. Никаких живых платных испытаний
этот документ не утверждает.
