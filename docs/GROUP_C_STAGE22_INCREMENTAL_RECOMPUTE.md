## Version and event boundaries

A "recompute" NEVER overwrites \`calculated_metrics.score_status=complete\`. PostgreSQL 003 defines a unique \`UNIQUE NULLS NOT DISTINCT (snapshot_id, config_id, previous_snapshot_id, creator_cohort_id, niche_cohort_id, prior_cohort_id)\` calculation version, and GC20 binds that row to a new immutable SHA/certified human review. **\`published_metadata_id\` is NOT in the unique score key.** Consequently, changing only the timestamp of an existing metadata record or replacing metadata_id without changing any other version dimension CANNOT create a second complete C7. A new source snapshot, a new approved config version or newly reviewed frozen cohort must supply a genuinely distinct calculation version. Reusing the old version with a changed publication is rejected as \`revision_version_required\` / \`c7_lineage_conflict\`; the old completed score must never be edited or silently relabelled. Legacy metadata fixes need a new immutable approved publication record, not in-place repurposing of historical evidence.

**An actual prior complete score and a NEW authoritative QDP handoff/run are preconditions.** Stage22 does not forge QDP events, fake new raw samples, create alternate run identities or choose unknown/unapproved alpha/k/priors. Existing GC04 intake has already accepted a QDP C preparation and durably inserted a **new** \`group_c_runs\` row and one matching \`group_c_jobs(job_kind='score')\` before \`plan\` can be called. There is exactly one Stage22 revision per new QDP run, \`revision=1\`; further changes require a fresh QDP run. No completed original run is reopened.

Four explicitly supported score recompute causes:
- \`new_snapshot\`: D1 appended a newer **actual** source observation; new run.previous_snapshot_id MUST be old complete score.snapshot_id, and pair must be latest two **unfiltered** source rows. New config/cohorts can also be reviewed in the new version.
- \`publication_correction\`: new canonical source_video_metadata.id for the same pinned raw pair, plus a distinct reviewed config/cohort/version to satisfy the authoritative SQL unique key. In-place published_at mutation is **not** a new version.
- \`cohort_changed\`: review signs new immutable frozen creator/prior/niche membership, while D1 sample/version stays the same. If config changes together with frozen cohorts, this specific reason has precedence over config-only.
- \`config_changed\`: review approves a distinct globally activated config/alpha/k/method version while source pair, publication and frozen cohort references stay the same.

\`source_revoked\`, \`manual_review\`, invalidation and pure quality failures are **not** made into a successful new C7. Stage24 owns retention and explicit invalidations, Stage23 owns quality statuses. A score job from a revoked source fails closed at GC20, never emits a result_ready outbox.

## \`PostgreSQLIncrementalRecompute.plan\`

Top-level autocommit PostgreSQL \`SERIALIZABLE\` transaction. Locks the **existing** new run and its score job \`FOR UPDATE\` and requires still \`queued\`, attempts=0, accepted original inbox/QDP hash. Reads a **previous certified complete** \`calculated_metrics\` + \`group_c_calculation_receipts\` AND an original completed Group C run in the same project/video/source. Rechecks live D1 rights and retention, verified current publication, raw quality/actual observed timestamps, newest 2 unfiltered source records, exact metric definition/version. Calls existing GC20 \`_reviewed\` verifier of *current* human decision and globally activated config; re-verifies all pinned peer source rights and frozen approvals. Plan does not call production IAM signing itself: **GC20 final commit must inject a trusted externally verified score-write IAM authority again**.

Pure \`determine_revision_kind(old,new)\` cross-checks evidence cause and continuity; \`_version_key\` reflects the existing authoritative SQL unique key. Invalid changes, missing approver, changed source, no truly distinct version or missing real QDP job fail closed. Creates one append-only \`group_c_revisions\` row (revision number 1), binding project/run/video + prior complete score ID + current QDP event/input SHA + exact source pair, publication metadata, config, signed review/activation IDs, frozen cohort IDs and GC08 publication SHA. \`evidence_sha256 = canonical_hash(payload)\` is a reproducible digest, **not** an IAM signature. Same run and identical requested revision replays idempotently; another cause or previous score for same run is \`revision_conflict\`. \`RevisionPlan.status=revision_planned_unpersisted_score\`: NOT an actual score and NOT a result ready event.

## Fenced worker completion and ready outbox

GC21 \`execute_score\` now reads an optional planned revision while its job+run are locked **in the same SERIALIZABLE transaction**. For any planned revision, it rejects a mismatched human review request and all changed pinned source/config/snapshot IDs. Calls GC20 \`persist(transaction_managed=True)\` requiring current trusted external IAM and the original complete C1–C7 recomputation. Under the **same transaction**, it marks run+job completed and calls \`PostgreSQLIncrementalRecompute.enqueue_ready(...,transaction_managed=True)\`.

\`enqueue_ready\` independently requires a matching certified complete new C7, unchanged original complete predecessor+evidence hash, correct frozen cohorts/review/activation, source permission and the still-latest exact raw D1 pair. Emits an **idempotent** pending \`group_c_outbox\` record with stable \`event_key=c7-revision:<UUID>\`, canonical SHA256 payload and all old/new result IDs and source/metric/config/review/freeze lineage, plus precise C7 score; existing DB trigger requires run completed and same persisted complete C7. On failure, both score and job completion roll back with the outbox insertion. On exact replay, the existing event ID/digest is returned, not duplicated; conflicting payload is rejected.

**No network sending to Analytics.** Only the durable pending event is prepared; GC-MOD-25 later owns delivery/ACK/retry. \`WorkerCompletion.revision_outbox_id\` is optional (None on a nonrevision GC21 run); \`RevisionOutbox.state=pending_analytics_delivery\` is NOT delivered/acknowledged.
