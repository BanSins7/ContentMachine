# Instagram Reels Top-100 — отдельный сервис Content Machine

## Запуск

Windows: START_INSTAGRAM_TOP100.bat из корня репозитория.
Адрес: http://127.0.0.1:8767/
React + TypeScript: instagram-top100-ui/
Backend: intelligence/instagram_top100/
CLI: python -m scripts.run_instagram_top100 --accounts "@user1,@user2" --scan-limit 500 --confirm-paid --confirm-rights

## Pipeline

1. Пользователь вставляет публичные usernames/URL. Поддерживается большой список (до 5000 в одном запуске).
2. По явно подтверждённой кнопке Bright Data **Reels — Collect all** (dataset `gd_lyclm20il4r5helnj`) получает ограниченную выборку Reels аккаунта. Используется асинхронный `POST /datasets/v3/trigger`, `type=discover_new`, **`discover_by=url_all_reels`**, `include_errors=true` и `notify=false`. Тело: `{"input":[{"url":"https://www.instagram.com/example","num_of_posts":100}],"limit_per_input":null}`. Параметры `start_date` и `end_date` для этого dataset недоступны с августа 2026; период с 1 ноября проверяется **только по подтверждённым датам** после получения данных.
3. Фильтрация требует подтверждённый Reel/video, автора или соавтора, дату, публичное количество просмотров; отсутствие данных не подменяется нулём.
4. Выбирается до 100 видео с наибольшим views на каждый профиль; не обещаем полноту истории аккаунта.
5. Для выбранных роликов вызывается существующий worker/local_worker.py::exact_download_job (подтверждение shortcode) с engine=off, без Whisper и платных LLM. Повторные файлы проверяются по source URL, shortcode и SHA-256.
6. Каждый шаг и snapshot_id сохраняются локально. При сбое повтор платного trigger при неизвестном результате запрещён.
7. После каждых **100 успешно скачанных и проверенных MP4** (по всем указанным аккаунтам суммарно) автоматически формируется отдельный ZIP. При завершении, отмене или частичном завершении оставшиеся 1–99 видео сохраняются в последний неполный ZIP. Исходные MP4 не удаляются и не перемещаются.
8. В каждом ZIP лежат MP4 в подпапках с именами аккаунтов, а также `manifest.json` (URL, дата, просмотры, SHA-256). Архивы создаются через временный файл с атомарной заменой. Созданные полные батчи переиспользуются после перезапуска; обновляется только изменившийся неполный батч.
9. В React появляются архивы с количеством файлов и кнопкой **«Скачать»**. ZIP передаётся сервером потоково и не загружается целиком в память.

## Папки

MP4: %USERPROFILE%\Downloads\InstagramArchive\<username>\<shortcode>.mp4
Метаданные: рядом с видео, shortcode.json
Состояния: %USERPROFILE%\Downloads\ContentMachineInstagramTop100\runs\<run_id>.json
Отдельные ZIP: %USERPROFILE%\Downloads\ContentMachineInstagramTop100\archives\<run_id>\batch_001.zip, batch_002.zip и далее.
Например: 100 MP4 = 1 ZIP; 230 MP4 = 3 ZIP (100 + 100 + 30).

## Настройка Bright Data прямо в UI

1. Запусти START_INSTAGRAM_TOP100.bat, открой http://127.0.0.1:8767/.
2. В поле **BRIGHT DATA API KEY** вставь API-ключ, нажми **Сохранить**.
3. После сохранения появится «Ключ сохранён». Значение ключа не возвращается в браузер и не хранится в localStorage; поле очищается. Замена ключа — вставить новый и снова сохранить.
4. Укажи публичные аккаунты, выбери глубину поиска и отметь оба подтверждения: возможная оплата Bright Data и права на хранение MP4. Только кнопка **«Начать сбор и скачивание»** отправляет платный запрос.
5. Действительность API-ключа проверяется реальным запросом к Bright Data после подтверждения запуска. Одно лишь сохранение ключа **не означает**, что провайдер проверил ключ.

Используется готовое локальное Windows-хранилище `studio_credentials.store`, защищённое Windows DPAPI (текущий пользователь). Ключ не записывается в React, job JSON, Git или незашифрованный .env. Разрешения на платный сбор относятся к *текущему запуску*; сохранение ключа не включает глобальные разрешения других инструментов Content Machine.

**Альтернатива:** по-прежнему можно указать `CM_BRIGHTDATA_API_TOKEN` через переменную среды или .env, но для этого отдельного сервиса это **не требуется**. Глобальные флаги `CM_BRIGHTDATA_METRICS_ENABLED` / `CM_BRIGHTDATA_METRICS_RIGHTS_VERIFIED` здесь также необязательны; они остаются для других инструментов проекта.

## Важные ограничения

- Источник может вернуть неполный список. После локальной проверки даты скачиваются только доступные и проверенные ролики с 1 ноября. Популярные Reels вне лимита scan_limit могут не попасть в результаты.
- Bright Data Reels Discover с августа 2026 **не принимает фильтры дат** и, по документации, может не предоставлять дату публикации. Если `date_posted` (или другой подтверждённый timestamp) отсутствует, Reels **не добавляется** в рейтинг. Гарантировать топ-100 за период без подтверждённых дат нельзя; альтернативный сбор через Instagram Posts Discover (с фильтрами дат) и отдельное обогащение метрик потребует отдельного дизайна и может привести к дополнительным расходам.
- Нет обхода приватных аккаунтов, авторизации, CAPTCHA, блокировок, rate limits.
- Несколько тысяч аккаунтов обрабатываются последовательно, а не одновременно.
- Возможен ручной resume по уже сохранённому snapshot_id, без повторного платного POST.
- Live Bright Data и Instagram MP4 в этой ветке не проверены. Обязательный тест на пользовательском ПК: 1 аккаунт + 1 MP4, затем тест 10 и 100.
- Нельзя считать отсутствие результатов подтверждением отсутствия публикаций.
- UI: cd instagram-top100-ui; npm install; npm run build. Dev UI: npm run dev (Vite 5174, backend 8767).


## Режим восстановления архивов

Кнопка **«Проверить ZIP»** в завершённом запуске запускает только упаковку уже скачанных файлов; новые платные Bright Data или Instagram-запросы при полностью завершённых аккаунтах не выполняются. При загрузке большого количества профилей архивы создаются из успешных MP4 по порядку их завершения, поэтому ошибка скачивания одного файла не блокирует накопление 100 других.

ZIP-экспорт не отправляет файлы в Haiku или другую модель: он предназначен для хранения и последующей пакетной обработки.


## Диагностика «Нет соединения с Bright Data»

Если аккаунты показывают «Проверить платный запрос» и 0 / 0 MP4, запрос мог быть принят провайдером до сетевого сбоя. Не повторяйте платный сбор, пока не сверены задания в истории Bright Data.

1. Нажмите «Проверить подключение (без оплаты)» рядом с Bright Data API Key. Выполняется только GET заведомо несуществующего snapshot: Reels не собираются, платный POST не отправляется.
2. Код dns означает ошибку DNS; timeout / connection — сеть, соединение или прокси; tls — сертификат HTTPS; HTTP 401 — ключ отклонён; HTTP 403 — доступ запрещён.
3. Ответ HTTP 404 на проверочный snapshot показывает, что API отвечает, но **не доказывает**, что ключ имеет права на Instagram Reels. Каждый платный запуск отдельно требует двух подтверждений.
4. Дополнительная диагностика Windows PowerShell: Test-NetConnection api.brightdata.com -Port 443. Значение TcpTestSucceeded True проверяет только TCP.
5. Сверьте ранее запущенные snapshots в Bright Data. Если платный запрос состоялся, не создавайте дубликат. Если в истории подтверждено отсутствие задания, можно делать новый запуск.
6. В новом запуске сначала выполняется бесплатный предварительный GET. Если он не удался, платные запросы не отправляются. Если первый платный POST вернул неопределённую ошибку, оставшаяся очередь аккаунтов сразу останавливается.

Статус «Ключ сохранён» подтверждает только локальное зашифрованное хранение. Не присылайте ключ или заголовок Authorization в сообщения об ошибках.


## Сбор завершился, но 0 Reels / 0 MP4

Это не подтверждает успешное получение публикаций. В карточке аккаунта раскрой подробности:
- «Получено записей» = количество записей Bright Data в snapshot (до фильтрации).
- «Отобрано с просмотрами» = публикации, которые прошли проверку принадлежности, даты, типа видео и просмотров.
- «Причины исключения» = суммарные количества записей по типу фильтра (вне периода, нет даты, нет просмотров, не Reel и т.д.).
- «Bright Data snapshot» = идентификатор уже оплаченного задания для проверки результата в Bright Data без нового trigger.

Сервис показывает «Нет подходящих Reels» вместо «Готово» для 0 MP4 после отбора, а записи с ошибками источника отдельно помечает как «Ошибка». Старые запуски без Reels также помечаются корректнее в новом интерфейсе.

Для диагностики без повторной оплаты открой последний локальный run JSON:
```powershell
$run = Get-ChildItem "$HOME\Downloads\ContentMachineInstagramTop100\runs\*.json" |
    Sort-Object LastWriteTime -Descending | Select-Object -First 1 |
    Get-Content -Raw | ConvertFrom-Json
$run.accounts | Select-Object username,status,observed,eligible,selected,rejected,error | Format-List
```
Если observed = 0 — проверь snapshot, период и наличие публикаций в Bright Data. Если observed больше 0, смотри rejected: возможно дата вне периода, отсутствуют просмотры или данные автора. **Не создавай новый платный запуск** для одной лишь диагностики.


## Изменение протокола Bright Data от 13.11.2026

Исходно в payload использовались `start_date`/`end_date`, удалённые из Reels API в августе 2026 года. Предпочтительный формат — объект `input` + `limit_per_input: null`; количество Reels ограничено `num_of_posts`. `include_errors=true` позволяет видеть строки с ошибкой Bright Data. Позднее нашли более точный режим для профиля: **`url_all_reels`** (Reels — Collect all), в отличие от общего `url` (Reels — Discover by URL). Оба режима официально документированы, поэтому переключение на `url_all_reels` — обоснованный выбор для массового сбора, **но не доказанное решение ошибок `dead_page`**.

Существующие Bright Data snapshot остаются неизменными. Исправление **не повторяет платные запросы** автоматически и не может исправить уже пустой snapshot. Запускай новую платную проверку только вручную после просмотра предыдущих заданий и понимания, что отсутствие даты в ответе может исключить все видео. Актуальная документация: https://docs.brightdata.com/api-reference/scrapers/social-media-apis/instagram-reels-discover-by-url и https://docs.brightdata.com/api-reference/rest-api/scraper/asynchronous-requests.


## Уточнение 13.11.2026: профильный режим и альтернативный парсер с датами

Официальные операции Bright Data с одним и тем же Reels dataset:
- **Reels — Discover by URL:** `discover_by=url` — допустимый режим поиска Reels по URL
- **Reels — Collect all:** `discover_by=url_all_reels` — специально для получения Reels профиля; выбран для инструмента
- Обе операции поддерживают `num_of_posts`; ни одна не поддерживает `start_date`/ `end_date`. Старые примеры вывода могут содержать `date_posted`, однако августовское обновление Bright Data предупреждает, что источник Reels теперь не раскрывает дату публикации. Нельзя гарантировать проверку периода с 1 ноября только этим dataset

**Альтернативный источник для дат:** Instagram **Posts — Discover by URL**: dataset `gd_lk5ns7kz21pck8jpis`, `discover_by=url`; поддерживает `start_date`, `end_date` и `post_type=Reel`. Однако пример ответа возвращает профиль с вложенным массивом `posts[]`, полем `datetime` и **без поля просмотров**. Этот путь можно использовать для отдельного получения Reels за период, но для сортировки **по просмотрам** потребуется получать и сопоставлять реальные view-метрики дополнительно (возможна отдельная стоимость). Нельзя автоматически переключаться на другой платный dataset после `dead_page` без отдельного подтверждения пользователя и без реализации сопоставления дат/просмотров.

Для диагностики ошибок `dead_page` передавай службе Bright Data snapshot ID, dataset ID, `discover_by` и URL профиля. Сначала сравни результат новых, **только вручную подтверждённых** вызовов в режиме `url_all_reels` с предыдущими `url`. Не повторяй платные запросы автоматически.
