# Bright Data → Market Intelligence (изолированная ветка)

## Реализовано
- API Bright Data Web Scraper, asynchronous trigger → progress → download.
- Публичные dataset IDs для TikTok posts, Instagram Reels, YouTube videos.
- Сбор метрик включается автоматически после регистрации ссылок и после
  обнаружения публикаций у автора, когда провайдер один раз настроен.
- Каждые 50 ссылок — отдельное долговременное задание в таблице jobs.
  ID Bright Data snapshot хранится без токена, повторные запросы делают
  progress/download, а НЕ ещё один платный trigger.
- Безопасное получение метрик до 2 000 уже известных публикаций в одном
  цикле постановки заданий. Лимит может быть ниже по платёжному тарифу.
- Данные сохраняются в общие videos/creators/metric_snapshots с
  source_policy_version_id, snapshot_key и сроком хранения.
- Метрики: просмотры, лайки, комментарии, репосты, сохранения — только
  когда соответствующие поля реально присутствуют у провайдера.
- Собственный MI performance.py сравнивает видео с медианой минимум
  5 других, возрастно-сопоставимых публикаций автора (±2x по возрасту),
  одинаковый источник, определение счётчика и платформа.
- Пользователю показываются коэффициенты просмотра в разах,
  baseline и объём сравниваемой выборки.
- POST /api/projects/<id>/market-intelligence/metrics с пустым JSON
  ставит на повторный сбор, GET .../metrics показывает состояние;
  сбор также запускается автоматически из /seeds и по завершении
  обнаружения публикаций из профиля.

## Однократная конфигурация администратора
В корневом локальном .env (он исключён из Git через .gitignore):

CM_BRIGHTDATA_API_TOKEN=<YOUR_NEW_TOKEN>
CM_BRIGHTDATA_METRICS_ENABLED=1
CM_BRIGHTDATA_METRICS_RIGHTS_VERIFIED=1

Последний флаг устанавливать только если проверены условия использования
Bright Data в своём тарифе и допустимость долговременного сохранения
метрик и их аналитики. Не вставлять ключ в браузер, тикет или чат.
Если ключ ранее раскрыт, выпустить новый. Перезапуск сервера для
автоматического фонового воркера — однократный.

Опциональные CM_BRIGHTDATA_*_DATASET переменные принимают идентификатор
пользовательского скрапера, если провайдер изменил публичный dataset ID.
Токен не передаётся ни в браузер, ни в jobs, ни в GitHub Actions.

## Периодический опрос уже известного видео
- Возраст <= 48 часов: новый сбор через 6 часов;
- от 48 часов до 14 дней: не чаще раза в сутки;
- старше 14 дней: раз в 3 дня.
Очередной запуск /metrics проверяет дедлайны. Отдельный системный
cron для повторного мониторинга без взаимодействия ещё не установлен.

## Ограничения
1. Эта реализация не повышает права на пользовательские Project Sources
   и не скачивает MP4. Для медиа действует отдельная политика.
2. Профильный сбор через yt-dlp пока ограничен 100 найденными видео;
   при блокировке не создаёт фиктивных публикаций.
3. Сопоставление обычных роликов зависит от полноты публикаций автора.
   Выборка из одних вирусных seed-video НЕ является корректным baseline.
   При <5 сравнимых роликах коэффициент = NULL.
4. Публичные поля Bright Data могут отсутствовать или быть неточными.
   Только целые фактические счётчики импортируются, отсутствие ≠ 0.
5. На уровне provider snapshot время фактического извлечения может
   отличаться от даты успешного download. observed_at фиксируется
   при получении snapshot; поэтому строгое внутридневное ускорение
   следует интерпретировать осторожно.
6. Последовательный запуск в локальном background worker без полного
   PostgreSQL + real Bright Data E2E ещё нуждается в проверке.
7. Реальный платный Bright Data trigger не выполняется в CI, а пользовательский
   API-токен не коммитится. Тестируются только offline фикстуры.
8. Новая интеграция не вызывает Group A/B/C; RTB V3 остаётся preview-only.
