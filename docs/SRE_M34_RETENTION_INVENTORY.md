# SRE M34 — Cross-Table Retention Inventory / Deletion Authority (2026-10-28)

**Branch:** `feature/sre-production-v1-20261023`, [Draft PR #22](https://github.com/BanSins7/ContentMachine/pull/22). Independent SRE schema-only inventory, not legal advice, not a claim of full physical erasure. Scope: source-specific `(project_id, content_version_id)` and SRE-generated records. **No changes were made to D1, RTB, analytics or main branches.**

## Why M34 cannot be fully certified yet

An SRE-only service can stop future *access* and future derivative writes under an immutable tombstone without destroying genuine receipts. It cannot delete or overwrite the original `sre_content_versions.content` while historical SRE LIVE items, M13 pair completeness, M26 dispatch intents, M28 receipts, M30 source proofs, M32 revision FKs and M33 snapshots still pin that immutable content revision. Blanket `ON DELETE CASCADE` risks eliminating the auditable evidence of a real paid operation and breaking model provenance. Upstream D1 video/source/request/observation lifecycles, provider-retained copies, exported analytics and infrastructure logs/backups are owned elsewhere, with separate retention requirements and authorization.

**Not equal:** `no longer readable` ≠ `physically deleted` ≠ `external processor erased` ≠ `backup erased`. The M34 API and scanner return each assertion separately; no output declares `full_physical_deletion_complete=true`. A limited primary-S3 table-row deletion certificate proves **logical row absence only**, not secure disk/backup/media removal.

## Explicit internal SRE controls

- `record_sre_source_revocation`: owner-scoped, exact content SHA; one transaction for tombstone and physical SRE disposable DELETEs.
- `record_sre_source_policy_revocation`: **requires D1 source/policy already disabled**; bounded ≤1,000 versions (no silent truncation) with idempotent per-version processing. Do not call policy-wide while D1 policy remains enabled.
- `record_expired_sre_content_revocations`: **explicit invocation only**, project/actor authorized; selects DB-time expired S3 versions or those beyond source retention-days; bounded page ≤100; re-run to cover newly expired versions. No scheduled background job was created.
- `process_sre_source_revocation_outbox`: M15 cancellation/replay; known UNKNOWN paid intent never silently retried. Outbox status is separate from physical deletion.
- `audit_sre_source_revocation_remnants`: same PostgreSQL REPEATABLE READ READ ONLY snapshot counts disposable M18 cache, S4 items/results/stages; S3 readable and LIVE results projection visibility; retained original S3 content, M23 quotes, M28 receipts, M30 pairs, M32 human judgments, M33 snapshots and pending cancellation events. **No SELECT of actual source JSON, prompt, reviewer note, model response or payment secret.** Returns `remaining_protective_invariant_violations` rather than hiding incomplete deletion.
- `inspect_sre_source_revocation`: `source_text_exposed=false`, **not** `source_text_present=false`: raw S3 content may remain stored behind the read barrier.

## Additional M34 control and remaining cross-branch integration requirement

The source tombstone now blocks claims **in the same transaction**: M11 active LIVE runs mark `cancel_requested=TRUE` immediately, S4 active runs are cancelled, and a durable outbox retains terminal M15 reconciliation. Direct privileged SQL cannot reset a run to active while its exact source is revoked. ACK requires terminal or M15-fenced UNKNOWN, never a bare cancel request. `audit_sre_source_revocation_remnants` exposes 20 exact aggregate counts, including still-active runs and primary-S3 deletion certificate.

A second authenticated host action `purge_sre_source_payload` is required for `purge_revoked_sre_primary_payload`. It refuses `rights_revoked`-only reasons, refuses any LIVE-pinned content and guarantees neither data-center secure overwrite nor external data deletion. It does not touch other modules. To actually meet full end-to-end retention, D1/RTB/analytics owners would need their own authorized event handling, output invalidation, logs/backups and processor retention controls; **do not directly edit their branches**.

3. Inventory every outward-facing export/analytics/metrics/log consumer and physical backups; SRE-only control is insufficient to guarantee delete at external processors.
4. Decide a legally/accounting-authorized retention window for immutable fee/consent/receipt/lineage records and segregate redaction from required audit custody.
5. Demonstrate caller-side D1 source revocation callback delivery and repeated sweeper invocation; current Python functions do no asynchronous work or automatic scheduling.
