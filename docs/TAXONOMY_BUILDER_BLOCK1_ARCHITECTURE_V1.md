## 2. Сквозной процесс (целевая пользовательская история)

~~~text
Мои проекты → Новый проект
           → заполнение и сохранение анкеты (существующий мастер)
           → явное подтверждение версии анкеты человеком
           → Taxonomy Pipeline Studio
           → настройка per-stage модели, reasoning, temperature, max_output
           → сохранение и явное утверждение Pipeline
           → расчёт ориентировочной стоимости
           ├─ «Изменить Pipeline» → новая конфигурация и новая смета
           └─ «Согласен» → отдельно подтвердить верхний бюджет
                           → явная кнопка «Запустить»
                           → LLM Fact Extraction
                           → автоматическая проверка структуры/цитат
                           → обязательное утверждение фактов человеком
                           → LLM Taxonomy Generation
                           → автоматическая проверка структуры
                           → [optional LLM Taxonomy Critic]
                           → проверка критериев человеком
                           → публикация immutable Research Taxonomy v1
~~~

Здесь принципиально **три разных человеческих решения** до расходования средств:
1. Подтверждение исходной анкеты: «ИИ будет работать именно с этой версией данных».
2. Утверждение Pipeline: «Модели и их настройки подходят».
3. Согласие с ориентировочной сметой и отдельное разрешение на **платный** запуск.

После Extraction добавляется четвёртое решение — утверждение фактов. Перед публикацией — финальное утверждение категорий.

Ничего не запускается автоматически от сохранения анкеты или Pipeline.

## 3. Карта экранов и статусная модель

| ID | Экран | Действие пользователя | Возможность вернуться |
|---|---|---|---|
| P0 | Мои проекты | «+ Новый проект» / открыть существующий | Список проектов |
| P1 | Анкета | Заполнить, создать/редактировать, сохранить | Черновик сохраняется локально |
| P2 | Проверка анкеты | «Подтвердить анкету» | Редактировать поля → новая ревизия |
| P3 | **Taxonomy Pipeline Studio** | Настроить/сохранить/утвердить конфигурацию | Вернуться к анкете |
| P4 | **Оценка стоимости** | Просмотреть этапы, допущения, диапазоны, лимит | «Изменить Pipeline» → P3 |
| P5 | **Согласие на расходы** | Подтвердить quote и лимит | Отказ → ни одного платного вызова |
| P6 | Готов к запуску | Отдельное «Запустить Taxonomy Builder» | Отмена до запуска |
| P7 | Выполнение Extraction | Статус, фактические расходы, ошибки | Перезагрузка восстанавливает вид |
| P8 | Что ИИ понял о продукте | Утвердить/править/отклонить/добавить факты | Пауза, Generation ещё не начат |
| P9 | Generation (+ optional Critic) | Статус, предложения, расходы | Остановка новых API-вызовов |
| P10 | Проверка категорий | Утвердить/править/отклонить/добавить | Можно оставить draft |
| P11 | Research Taxonomy | Просмотр immutable версии, истории решений | Возврат к проекту / создать v2 |

### Серверные состояния (продуктовая схема, не названия SQL ENUM)

~~~text
intake_draft
  → intake_saved
  → intake_confirmed
  → pipeline_draft
  → pipeline_approved
  → quote_required
  → quote_ready
  → spending_authorized
  → ready_to_run
  → extraction_running
  → fact_review_required
  → generation_running
  → topic_review_required
  → taxonomy_approved
~~~

Дополнительные статусы: `validation_blocked`, `awaiting_model`, `paused_budget`, `failed_provider`, `invalid_model_output`, `cancelled`, `stale_profile`, `stale_quote`.

Состояние вычисляется сервером из сохранённых версий/согласий/запусков. В браузере нельзя просто отправить `state=approved` и пропустить этап. Встречающиеся действия должны быть идемпотентными.

### Возвраты
- P2 → P1: изменение исходных данных увеличивает `profile_revision`. Старое утверждение **не переносится**.
- P3 → P2: можно вернуться и изменить анкету; сохранённый Pipeline относится к старому `profile_hash`.
- P4 → P3: после изменения модели, reasoning или temperature возникает **новая версия Pipeline**. Старую смету и consent использовать запрещено.
- P5 «Не согласен» не расходует средства, возвращает к P4/P3/P0.
- P7→P8: раннер обязан остановиться и ждать действий пользователя, нельзя автоматически запускать Taxonomy Generation.
- P8: факт, исправленный человеком, сохраняется как новое значение со ссылкой на старое; автоматически пересчитать budget remaining перед следующим LLM-вызовом.
- P9→P10: Critic может оставить замечания, но не утверждать тему самостоятельно.
- Изменение анкеты во время уже начавшегося запуска не изменяет его snapshot; для новой версии создаётся новый run.

## 4. Анкета: что необходимо для Builder (контракт Block 2)

**Существующую девятишаговую анкету не заменять**. Builder использует отдельную строгую проверку *готовности к анализу*. Старые проекты и черновики продолжают открываться.

| Поле | Сегодня | Правило подтверждения для Builder |
|---|---|---|
| `project_id` | Существует в локальном проекте | должен разрешаться в PostgreSQL project registry |
| `niche` | Произвольный текст | в v1 строго Health & Fitness, код `health_fitness` |
| `goal` | Сохраняется старой формой | Builder его игнорирует; цель `maximize_views` системная |
| `product_type` | Предварительный enum | обязательно, включая `no_product` |
| `product_functions` | Свободный текст | обязательно кроме `no_product`; нельзя угадывать |
| `audience_problems` | Свободный текст | обязательно; иначе просить уточнение |
| `product_description` | Свободный текст | только дополнительный контекст |
| Research documents | Файлы на диске | список+права+объём; содержание отдельно парсится в Block 6 |

Предварительный enum текущей формы: `mobile_app`, `digital_service`, `physical_product`, `service`, `course`, `no_product`, `other`; это не финальный навсегда список.

**Важно:** `GET /taxonomy-input` — это *снимок*, а не событие human approval. В следующем блоке появляется отдельное подтверждение текущей `profile_revision/profile_hash`.

Если PostgreSQL выключен, неполон или mirror вернул `unavailable/migration_required/revision_conflict`, анкету можно сохранить локально; Pipeline approval и платный Run заблокированы с конкретным объяснением.

Если выбран `no_product`, Builder может генерировать темы на основании утверждённых проблем и контекста, но **не придумывает функции отсутствующего продукта**.

## 5. Taxonomy Pipeline Studio — отдельный граф и функции

~~~text
[Fact Extraction · required LLM]
           ↓
[Source/JSON Validation · required deterministic]
           ↓
[Human Fact Review · required]
           ↓
[Taxonomy Generation · required LLM]
           ↓
[Taxonomy Validation · required deterministic]
           ↓
[Taxonomy Critic · optional LLM]
           ↓
[Critic Validation · required if enabled]
           ↓
[Human Topic Review · required]
           ↓
[Approved Research Taxonomy]
~~~

**Нельзя удалить Fact Extraction или Taxonomy Generation и нельзя отключить Human Reviews.** Менять местами причинно-зависимые этапы тоже нельзя. В MVP свободная настройка относится к моделям и параметрам внутри LLM-ролей, а также включению Critic.

### Роли
- `fact_extraction`: LLM получает утверждённый снимок анкеты/доступного текста; извлекает атомарные функции/проблемы со ссылкой на точную исходную цитату и нормализованным именем. Не утверждает факты.
- `taxonomy_generation`: LLM получает **утверждённые человеком** функции и проблемы; создаёт `direct`, `problem_related`, `adjacent`; у каждой темы name, definition, include, exclude, положительные/отрицательные иллюстративные примеры, related fact IDs, origin (`explicit`, `inferred`, `user_added`) и review status.
- `taxonomy_critic`: другая или та же модель получает исходные правила и выдаёт **замечания**, например пропущенные проблемы, избыточное пересечение и необоснованную функцию. Critic не переписывает silently утверждённый объект.

### Per-stage настройки

| Поле | Семантика |
|---|---|
| `model_ref` | конкретный провайдер + модель + ревизия её возможностей |
| `reasoning.mode` | `auto`, `effort` или `budget_tokens`, только если реально поддерживается |
| `reasoning.effort` | доступные именно этой модели: например `none/low/medium/high`, не универсальный фиксированный набор |
| `reasoning.budget_tokens` | числовой режим при поддержке провайдера; диапазон проверяет registry |
| `temperature` | `null` или число в разрешённом диапазоне; сочетания с reasoning также проверяются |
| `max_output_tokens` | лимит вывода стадии; thinking tokens могут влиять на стоимость |
| `prompt_version` | неизменяемая версия системных инструкций стадии |
| `enabled` | true для основных 2 стадий, настраиваем только Critic |
| `failure_policy` | ошибки API/JSON не считать успешным «uncertain» |

Особенно важно: **поддержка temperature может зависеть от включённого reasoning**. Поэтому одного флага `supports_temperature` мало: нужны ограничения для конкретной комбинации `model + reasoning.mode/effort + temperature + response format`.

### Настройки Studio и маршрутизация
- «Новая конфигурация», «Сохранить черновик», «Дублировать», «Вернуться к прошлой», «Утвердить».
- Смена модели сразу обновляет возможные reasoning modes, допустимые температуры, максимальный output и schema support.
- Если модель не умеет выбранное, пользователь видит объяснение, сервер **отклоняет** настройку, адаптер не «исправляет молча».
- Изменение уже утверждённой конфигурации создаёт v2 с новым checksum.
- Смена модельного alias в каталоге никогда не изменяет старый approved run: запуск использует exact version snapshot.

Для пользователя цель: поменять GPT → Claude или reasoning medium → high за несколько действий без кода и без потери знаний проекта.

## 6. Реестр моделей: версия возможностей, не хардкод

Логически общий **Model Capability Registry**; Taxonomy Builder использует свои stage contracts, SRE — другие. Реестр должен хранить:

- `provider`, `provider_model_id`, `model_ref`, `catalog_revision`, `model_version` и `availability`.
- Supported tasks, `supports_json_schema`, `reasoning_modes`, `effort_options` / budget min-max.
- `temperature` min/max и **матрицу запрещённых сочетаний** с reasoning/structured outputs.
- `context_window`, `max_output_tokens`, сведения о тарифицируемых reasoning tokens, provider-specific fees.
- `input/output price per million`, валюта, дата проверки, источник тарифа, возможные отдельные ставки.

**Не зашивать цены и capabilities в UI.** Недоступную/непроверенную модель нельзя использовать в утверждённом платном запуске. Нельзя считать, что общий OpenRouter-ключ уже гарантирует поддержку любых параметров.

Модели для первого теста можно выбирать отдельно, но без подписанной capability revision конкретные настройки ещё не готовы к выполнению.

## 7. Смета после Pipeline Approval и согласие с расходами

Порядок: **Pipeline approval → Quote → Spending consent → Explicit Run**.

### Что показывает окно P4

Для каждого включённого этапа:
- model ID, reasoning/temperature, max tokens, версия промпта;
- прогноз input/output billable tokens (reasoning входит туда, где это платно);
- **низкая / типичная / повышенная** стоимость, источник/дата тарифа;
- разбивка по 2 обязательным и 1 опциональной стадиям;
- предупреждения об объёме документов/неопределённости, ретраях и возможном дополнительном тарифе.

Математическая основа:

~~~text
estimated_stage_usd =
    input_tokens_estimate  * input_price_per_token
  + billable_output_tokens_estimate * output_price_per_token
  + any verified provider-specific fees
~~~

Эта оценка **не является гарантией верхнего потолка**. Отдельно пользователь подтверждает `max_authorized_spend`, а runner перед каждым платным запросом проверяет оставшийся бюджет, доступность цены и соответствие model capability snapshot. Если лимита недостаточно — останавливает новые API-вызовы и запрашивает новое согласие.

### Политика quote и consent
- Quote: immutable `quote_id`, `profile_revision/hash`, `pipeline_id/config_checksum`, `price_snapshot`, `assumptions`, `generated_at`, `expires_at`, currency.
- User consent: immutable `consent_id` → ровно один quote; approved limit, user, timestamp; может быть отозван до старта.
- Quote устаревает при изменении анкеты, Pipeline, тарифа, оценённого набора источников/документов или expiry.
- Если неизвестна цена модели или невозможно оценить значимый файл, **не создавать фиктивно точную смету** и не открывать платный Run без явного решения проблемы.
- Если после P8 утверждённых фактов оказалось значительно больше, пересчитать остаток и при необходимости снова показать quote/consent.
- Отмена работающего процесса останавливает новые вызовы, но не обещает возврат уже потраченных денег.
- Никаких автоматических стартов при сохранении проекта, Pipeline или подтверждении бюджета.

**Отдельно:** эта смета касается только Taxonomy Builder; затраты на D1/D2 scraping и SRE-классификацию сюда не включаются.

### Инварианты
1. Все операции с проектом имеют проверку `project_id`, а будущие HTTP handlers проверяют владельца/право доступа.
2. Утверждение анкеты закрепляет точные `profile_revision` + `profile_hash`. Новая ревизия его не наследует.
3. Утверждение Pipeline закрепляет exact config + provider/model capabilities + prompt versions.
4. Consent относится к exact quote/config/profile; никогда не переносится после изменения.
5. Каждый Run требует актуального согласия и уникального ключа запуска против повторной оплаты.
6. Результаты и попытки append-only (история), редактирование approved taxonomy только через новый draft/version.
7. Generation нельзя запускать до утверждения фактов **этого** проекта/запуска/профиля.
8. API-ключи/секреты никогда не передаются браузеру, не попадают в логи или в модельные снимки.
9. Если пользователь редактирует анкету или Pipeline, уже выполненные запуски остаются привязаны к старым версиям.
10. Для перспективы database-per-project использовать абстрактный репозиторий; для MVP shared DB с проектной изоляцией.

**Миграционный риск:** в main есть `003_taxonomy_intake.sql`; PR #6 существует в отдельной ветке с миграциями другого контекста. В блоке 3 нужно сначала сверить уже влитые версии и лишь затем назначить новый номер миграции; нельзя исправлять ранее применённый SQL задним числом.

## 9. Планируемый HTTP API (ещё не реализован)

Базовый путь (предложение): `/api/projects/{project_id}/taxonomy-builder`.

| HTTP | Эндпоинт | Действие |
|---|---|---|
| GET | `/state` | Серверный текущий этап и версия исходных данных |
| POST | `/intake/confirm` | Подтверждение анкеты по ревизии/хешу |
| GET | `/models` | Доступные проверенные модели и режимы |
| GET | `/pipelines` | История черновиков и версий |
| POST | `/pipelines/draft` | Создать/изменить черновик с optimistic revision |
| POST | `/pipelines/approve` | Неизменяемая утверждённая версия |
| POST | `/quotes` | Оценка цены по approved config |
| POST | `/consents` | Явное разрешение затрат по quote и сумме |
| POST | `/runs` | Реальный запуск по consent + idempotency key |
| GET | `/runs/{id}` | Статус выполнения, расходы, ошибки, ожидаемый review |
| POST | `/runs/{id}/facts/review` | Подтверждение/исправление извлечённых фактов |
| POST | `/runs/{id}/topics/review` | Подтверждение/исправление направлений |
| POST | `/runs/{id}/publish` | Публикация approved taxonomy |
| POST | `/runs/{id}/cancel` | Остановить будущие платные действия |

Ни один endpoint выше не считается уже действующим. На сервере обязательны per-project authorization, version checks и транзакции/идемпотентность. Браузер не может передавать произвольный «статус» для пропуска человеческих gates.

## 10. Дизайн: спокойный ChatGPT-подобный workspace

Не копировать чужие логотипы или брендинг. Использовать принципы интерфейса: контрастная типографика, нейтральная палитра, удобная навигация, большие поля ввода, понятные последовательные действия.

- **Sidebar**: проекты, «+ Новый проект», текущий проект, Taxonomy Builder, документы, настройки; downloader tools оставить.
- **Top progress**: «Анкета → Pipeline → Смета → Запуск → Факты → Категории».
- **Основная область**: максимум ~900–1000px ширины, читаемый контент, светлая/тёмная темы, минимум декоративных блоков.
- **Taxonomy Pipeline Studio**: слева компактный список этапов, справа настройки выбранной стадии; на узких экранах всё в одну колонку.
- **Контролы**: searchable model selector, reasoning dropdown, temperature slider/number при поддержке, поле max output, inline объяснение недоступной комбинации.
- **Только одна главная кнопка на экране**: «Подтвердить анкету», «Утвердить Pipeline», «Согласиться с бюджетом», «Запустить».
- **Смета**: фактические тарифы с датой, invoice-like разбивка, низкая/типичная/повышенная цена, отдельно budget consent; никаких цветных «99% точная стоимость».
- **Review**: раскрывающиеся карточки с исходными цитатами и понятными принять/изменить/отклонить; JSON по желанию в технических подробностях.
- **Доступность**: labels, keyboard focus, aria статусы, responsive, no fake controls.

Существующие downloaders / Discovery routes не удалять, не менять их API ради UI Taxonomy Builder.

## 12. Явно открытые вопросы

1. **Модели и тарифы.** Конкретные модели, цены, актуальные возможности необходимо проверить в блоке 3/5. Не хардкодить будущую модель на основании названия или неподтверждённого прайса.
2. **Точный список product_type.** Текущий enum предварительный и совместим с текущей анкетой.
3. **Исследовательские документы.** Их извлечение/токенизация/стоимость требует отдельного контракта на блоке 5/6.
4. **Изоляция базы.** Shared PostgreSQL + project_id для MVP, database-per-project оставлено как вариант дальнейшего размещения.
5. **Согласование PR #6.** Не плодить две параллельные «истины» Taxonomy; перед новыми миграциями сверить текущее состояние веток.

**Ключевой итог:** пользователь самостоятельно создаёт проект, подтверждает версию анкеты, настраивает конкретные модели и параметры reasoning/temperature в отдельном Taxonomy Pipeline Studio, утверждает конфигурацию, видит предварительную стоимость, отдельно разрешает платные запросы и запускает Builder. Между извлечением фактов и генерацией категорий и перед публикацией обязателен человек. Версии анкеты, конфигурации, цены, согласия и результатов сохраняются независимо.

**Стоп после блока 1.** Ни один SQL/Python/JS файл ранее подготовленного черновика ещё не должен попадать в этот коммит.
