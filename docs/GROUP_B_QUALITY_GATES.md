## Review storage and immutable revisions

Stage23 reuses the existing migration `055_group_b_runtime.sql` table `group_b_review_events` and its immutable `BEFORE UPDATE OR DELETE` trigger. There is **no extra B database, migration or edit of completed SQL005 B rows**. `review/contracts.py`, `review/repository.py` expose:

- `make_decision(...)` creates a versioned SHA-256-canonical `ReviewDecision` with exact `content_b_analyses.id`, `analysis_key`, original source evidence manifest SHA, `previous_revision`, `previous_sha256`, whitelisted B1–B8 block/target/field, immutable SQL005-compatible value, original evidence references and rationale. Gold examples additionally carry a separately versioned `gold_version` and deterministic `sample_key` derived ONLY from original analysis/block/target/index/field.
- `append_review(conn,project_id,run_id,reviewer_id,expected_revision,decision,admission_verifier)` enters an atomic caller/own transaction, locks `group_b_runs`, checks the project/run/SQL005 parent, current source and policy rights, exact original source manifest/hash/pin, current append-only event revision/SHA chain, target SQL005 row, and effective whole-row domain constraints. Concurrent stale reviewer writes fail. **Idempotent replay** returns the same revision only for the same reviewer and the *exact* existing decision SHA. Nothing is silently overwritten.
- `verify_human_review_admission(project_id,run_id,reviewer_id,decision,original_row,effective_row,prior_decisions)` is an **injected, mandatory, independently trusted** authority. It must check authenticated reviewer role and non-self-approval when required, project rights and latest media/QDP/Group A identities, real source-backed quote/frame/timeline for that correction (especially B4 `ai_generated`, B5 cutting metrics, B6 `none`, B7 CTA destination, B8 exact approved taxonomy), actual provider receipts, and original evidence provenance. Synthetic test callback is **not a production authorization**.
- Original B1–B8 SQL005 result history is **immutable**; the derived `read_effective_labels(conn,project_id,run_id,admission_verifier)` computes the approved human-correction overlay in revision order, without rewriting the originals, under a database run SHARE lock and independently injected `verify_human_review_effective`. Unsupported targets, missing source/proof, invalid B2/B3/B5/B6/B7/B8 cross-fields, revoked rights or stale analysis/policy are hard failures.
- Stage22 `read_group_b_result` now exposes `human_review_revision`, `has_human_corrections` and `qualified_for_downstream`. **Any human correction marks the baseline result ineligible for downstream qualification**, even if its untouched SQL005 parent says `completed`. A review **does not magically make automatic inference valid again**; stage24 will explicitly invalidate and refresh the signed downstream lineage before stage25 Analytics handoff.
- There is no implicit promotion of `needs_review` to `completed`. Gold annotations **never** change effective labels.

### Permitted edits

The v1 editor enforces conservative **field-level** corrections over existing SQL005 rows only. B1 hook mechanism/delivery/flags, B2 video/carousel format, B3 indexed role/phase, B4 three visible booleans and nullable AI provenance, B5 source-measured edit type/cut metrics, B6 3 subtitle types and style, B7 indexed CTA/destination fields, B8 existing approved category/topic/subtopic IDs are supported. Source-backed text itself and B7 occurrence counts/positions cannot be invented or edited in this stage; a new original source scan and version is required instead. New B8 taxonomy IDs/slugs/merges require authorized registry governance, not a reviewer-supplied ID. All changed values must be confirmed by an independent host; field validators additionally check whole-row constraints (e.g. a B5 cut count cannot contradict single_take; a B8 subtopic must actually belong to that topic; subtitle `none` cannot retain style).

## Versioned gold sets

- `review/quality.py`: `select_gold_candidates` deterministically hashes original target identity and version and samples up to `per_block` from each of B1–B8; `gold_split(version,sample_key)` creates stable disjoint 20% calibration and 80% evaluation buckets. No random seed or model-prediction-dependent sample selection. **Never evaluate quality on calibration/training examples**.
- Human gold annotations are immutable `group_b_review_events` with `kind=gold_annotation`, exact source analysis, independent reviewer and original ref pins. Two independent annotators are the minimum for any admitted consensus. Unreviewed and contradictory pairs are **disputed** and cannot be treated as negative/false or considered gate-passing.
- `load_gold_set` loads annotations only for the requested project and explicit gold version, verifies each full original version and review digest, and reads the **original automatic SQL005 prediction** (never the human-corrected overlay) under a separately trusted `verify_gold_annotation` authority. It binds the evaluation report to `gold_sha256`, `gold_version` and immutable review labels. Additional annotations change the effective gold digest and require rerunning/repinning the evaluation; a report is not a standalone authorization to publish.
- `evaluate_quality` computes original-model **per-class TP/FP/FN, support, precision, recall and F1**, macro precision/recall, calibration/evaluation counts, disputed/unreviewed count, pairwise human agreement and two-reviewer Cohen's kappa when defined. Explicit nullable/unknown labels do not silently become negatives. `QualityPolicy` defines minimum evaluation samples, per-class gold support, precision, recall, reviewer agreement and optional required class list. Missing support/low agreement, disagreements, insufficient samples or any target below threshold results in `quality_gate=blocked` rather than a made-up pass.
- `evaluate_project_quality` is a convenience composition of real project-scoped SQL gold loading and scoring. This does **not** itself grant downstream Analytics eligibility.
