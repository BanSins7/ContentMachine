## Why a separate append-only diagnostic ledger?

Authoritative \`003_performance_c.sql\` only permits \`calculation_status\` and \`score_status\` values: \`complete\`, \`insufficient_data\`, \`pending_configuration\`, \`invalid_timestamp\`, \`incompatible_source\`, \`counter_correction\`, \`calculation_error\`. It does not permit arbitrary fine-grained reason codes; \`complete\` requires fully consistent C1/C3/C5/C6/C7 math and original raw evidence. Rewriting historical \`calculated_metrics\` or inserting fake zero/NULL C7 to represent invalid data is not authorized. We add **\`intelligence/migrations/061_group_c_quality_reports.sql\`** only (no edits to 003/004/056–060).

New \`group_c_quality_reports\` captures one immutable terminal diagnostic per exact **failed score job**, with project/run/video/job, original source/policy/current+previous snapshot, metadata/config IDs, stable original reason code, one of the 6 allowed non-complete \`calculation_status=score_status\` values, \`severity=blocked|anomaly\`, \`diagnostic_version=group-c-quality-gate/v1\` and canonical SHA-256 fingerprint over original IDs/status. Unique job/run/digest prohibit duplicate or reassigned classification. FK and trigger require that the original \`group_c_runs.state=blocked\`, \`group_c_jobs.state=failed\`, both refer to the same project/video, that the error code matches **both** and that no \`calculated_metric_id\` was persisted. UPDATE/DELETE quality report is always rejected. **No raw counters or user content** are copied to the diagnostic table: DB retains authoritative raw sources unchanged; this also avoids copying sensitive/expired raw facts after revocation.

This ledger is for **negative quality outcomes** only. It is **not** a \`calculated_metrics\` record or an Analytics score-ready event, and a blocked run is never silently requeued as healthy. To reprocess corrected source facts, GC22 requires a new real QDP preparation/revision with proper original signed human approvals; GC24 owns lifecycle invalidation/revocation of previously complete scores.

## Pure \`metric_quality_gate.py\`

- \`classify_quality_failure(ContractError)\` returns a typed immutable \`QualityDecision\` only for known original evidence failures; unknown exceptions and IAM/lease/SQL failures return \`None\` (never mislabel an authentication failure as metric quality).
- The **original** C0/D1 error remains the precise \`reason_code\`. Explicit mapping is \`incompatible_metric_definition\`, \`incompatible_metric_version\`, source/policy/TTL/retraction/lineage => \`incompatible_source\`; negative corrected view counters => \`counter_correction\`; missing C0 V/L/C/S, undefined views=0, insufficient peers => \`insufficient_data\`; malformed observed/published timestamps => \`invalid_timestamp\`; missing/not-activated signed config or unapproved review => \`pending_configuration\`; approved growth anomaly or deterministic calculation overflow => \`calculation_error\`. No source values are coerced to zero, capped, rounded to a fake score or ignored via “last good” fallback.
- \`approved_growth_limit(config.growth_policy)\` recognizes optional reviewed field \`max_views_growth_per_hour\` only as an **exact positive base-10 decimal STRING with <=12 decimal places**, valid for \`NUMERIC(30,12)\`. A JSON float/NaN/exponent/non-positive value is rejected as \`invalid_growth_policy\`. **An absent field has NO approved limit, and the system does not claim that huge growth was checked against a universal threshold.** No unstated heuristic or magic number is introduced.
- \`reject_anomalous_growth\` recomputes original views/hour using GC15 exact Decimal, compares to signed approved threshold only if set, and raises \`growth_anomaly\` if original raw exceeds bound; no cap, no invented \`max\`, no score. Equality is valid. All sample IDs/source/view version still checked by GC20.

## Integration with GC20 and GC21

GC20 re-reads approved immutable config \`growth_policy\` inside its existing SERIALIZABLE review/source/peer/IAM transaction. The \`reject_anomalous_growth\` gate runs *before* complete C7 persistence. If exceeded or malformed, the GC20 transaction rolls back with its typed source error. Existing successful C7 formula and idempotency/fingerprints remain unchanged.

GC21 \`run_once\` catches the failed calculation and asks \`classify_quality_failure\` for an exact terminal evidence reason, **without accepting generic SQL exceptions as quality**. It then calls \`fail(...,quality_decision=...) \` in one transaction, re-verifies the original live lease fencing and marks the job \`failed\`, run \`blocked\`, both with original code, and inserts immutable \`group_c_quality_reports\`. If report fails to insert due to mismatch, the **entire job/run terminal transition rolls back**; it cannot report false success. A retryable transient (e.g. \`40001\`) continues GC21 bounded retry path, never creates a quality report. IAM denial stays ordinary nonquality failure and **never creates a diagnostic implying valid data**.

The returned \`WorkerFailure.quality_report\` is either a typed \`PersistedQualityReceipt\` with \`state=blocked_unscored\` or \`None\` for a nonquality error; \`WorkerFailure.state=failed\` remains the actual job state. No \`group_c_outbox\` item is generated by blocked quality runs and no QDP success acknowledgement is issued.
