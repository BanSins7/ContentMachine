## Source-of-truth constraint

Group C GC20 remains **the only source allowed to calculate and write C7**. Analytics must consume the **already persisted and certified** \`calculated_metrics.id\`, not call another scoring function nor independently INSERT into \`calculated_metrics\`. Exact lineage is project/video ID, run ID, metric snapshot+prior, publication metadata, source/policy, metric definition+version, approved config, frozen creator/prior/(optional) niche member/cohort versions, human review+decision+activation, certificate \`evidence_sha256\`, four stored Decimal components and exact \`breakout_score\`.

Implementation \`intelligence/group_c/analytics_bridge.py\`:
- \`PersistedC7Handoff\`: immutable typed result of **reading actual SQL \`calculated_metrics\` and \`group_c_calculation_receipts\`**, Decimal only, never a calculated score. Only validates the already stored four-part invariant.
- \`PostgreSQLAnalyticsBridge.load_persisted(...)\`: project-owned certified completed GC20 C7, verified GC24 current-rights gate and every peer's TTL, then returns the real numeric results. Cross-project/missing scores are indistinguishable. \`transaction_managed=True\` joins an externally owned SERIALIZABLE PG transaction for an exact Analytics-side DB adapter; no separate snapshot.
- \`PostgreSQLAnalyticsBridge.enqueue_baseline(...)\`: after a **first completed** GC21 C7 run+job, creates a \`group_c_outbox(event_type='group_c.result_ready/v1')\` event with exact four C7 Decimal components, source/policy and all lineage, immutable JSON+SHA. Called **inside the same fenced SERIALIZABLE worker transaction**; if any INSERT fails the C7, run/job completion and new outbox all roll back. No duplicated event for GC22 revision: GC22 itself already wrote one \`c7-revision:<revision UUID>\` event with previous and new certified C7 IDs. Concurrency and exact replays return the same original event.
- \`_validate_outbox_payload\`: checked on delivery against actual \`calculated_metrics\` + original signed GC20 certificate; must match project/run/video/source/metric version, current and prior snapshots, publication, config, frozen cohort IDs, review decision+activation, original evidence SHA and original Decimal C7. Existing GC22 revision events are compatible even though their original event shape did not include each individual component; their four components are loaded exclusively from original persisted SQL.
- \`PostgreSQLAnalyticsBridge.deliver_one(...)\`: exclusively a **same-PostgreSQL-database** synchronous outbox/Analytics-adapter operation. Begins SERIALIZABLE transaction, requires live \`GroupCPorts.analytics\` capability \`group-c-analytics-outbox/v1\`, claims one project-pending outbox row \`FOR UPDATE SKIP LOCKED\`, checks its immutable hash and the exact certified C7, then repeats the full GC24 current-rights/TTL/raw-latest/frozen-peer check. If no longer eligible, marks event \`failed\` in this transaction, returns \`state='blocked'\` and **sends no numeric score**. Otherwise calls \`analytics.enqueue_persisted_result(conn,project_id,calculated_metric_id,idempotency_sha256)\` on this exact same connection and same transaction. Requires durable ACK \`{accepted:true,project_id,calculated_metric_id,idempotency_sha256,analytics_snapshot_id:<positive integer>}\` matching the original event; THEN and only then marks outbox \`delivered\` with \`delivered_at\`. Invalid ACK, unavailable peer, SQL failure or conflicted payload roll back all data and never claim delivery. A second delivery of a delivered event is a no-op. This is **not** remote HTTP and cannot use a sink that commits on a different DB connection or merely promises to enqueue later.

Important distinction: a caller can still read historical complete \`calculated_metrics\` through privileged raw SQL; production roles MUST restrict those unguarded reads and send all Analytics consumption through the GC24/25 gate. No blanket RLS/SQL permissions are invented by this module. TTL and revocation can occur after an external RPC starts; this design avoids that network race by requiring a same-DB transactional sink. An out-of-DB Analytics installation will need an independently reviewed protocol, not an unverified HTTP ACK.
