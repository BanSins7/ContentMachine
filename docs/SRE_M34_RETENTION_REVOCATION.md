## Critical semantics

SRE M34 does NOT equate a revocation callback with total deletion. It immediately blocks SRE retrieval and new derived processing for an exact tenant-scoped D1 content version, physically removes disposable M18 embedding vectors and S4 offline item contexts and S4-only fake result/evidence rows in the same transaction, and persists an immutable source tombstone plus LIVE run cancellation outbox. Immutable M25–M33 financial/receipt and integrity evidence are never purged. Original S3 content remains stored for LIVE-pinned and other FK-pinned versions; for a strictly unreferenced, separately authorized S4-only version the optional primary-row purge may remove that S3 row and issue a certificate without claiming backup/secure overwrite. The system reports this limitation explicitly and will NOT answer `full_physical_deletion_complete=true`.

This design protects against silent regrant of revoked content, re-creation of a cache, invented UNKNOWN financial refund/retry, and loss of pending cancellation after process crash. True source erasure involving D1 source-of-truth retention, immutability FKs, provider-side retention, logs/backups and connected modules requires separately coordinated authority and data lifecycle decisions; **SRE cannot guarantee deletion of third-party copies or external D1 database**.

## M34 continuation — atomic fail-stop and selective primary S3 purge

**Immediate stop after revocation, not eventual-only cancellation:** Migration 068 now sets `sre_live_runs.cancel_requested=TRUE` for every nonterminal LIVE run referencing the tombstoned source in the same transaction as permanent read denial; this blocks M14 LIVE claim/heartbeat and M15 paid-intent advancement before any outbox worker runs. M15 then performs real lease-fenced terminal cancellation; the M34 outbox **cannot be acknowledged** just because `cancel_requested` was set on an otherwise active run. SQL ACK now requires genuine terminal state or a pre-existing M15-fenced `unknown + cancel_requested`. UNKNOWN without a proven M15 cancellation remains outstanding. A direct UPDATE cannot reverse the LIVE stop flag while the revoked source remains pinned.

**S4 fail-stop is atomic too:** An affected active S4 run changes to `status=cancelled,cancel_requested=TRUE` and its legacy fixture run becomes cancelled; late workers cannot claim it or recreate the physically removed S4 results/stage metadata. SQL directly rejects resetting `sre_offline_runs` to queued/running for any retained offline source-revocation fence. Already-completed S4 history is not falsely rewritten as a new prediction.

**Separately authorized primary S3 deletion (limited):** `purge_revoked_sre_primary_payload` requires a second trusted host permission `purge_sre_source_payload`, the exact tenant/source SHA, an existing permanent tombstone with `privacy_delete`, `source_deleted`, or `retention_expired` reason, and **no LIVE/S4/derived/cache dependency**. It executes a guarded primary-table `DELETE FROM sre_content_versions` in its own atomic transaction. Any remaining LIVE foreign key / evidence or unexpected FK denial fails closed and does not erase the earlier tombstone. A new `sre_source_payload_purge_certificates` table permanently attests that the exact S3 row is absent under the original source pin; direct forged certificates, changes and deletions are forbidden by SQL. A repeated purge or repeated source tombstone call is idempotent even after the primary row has been removed. A new S3 `BEFORE INSERT` guard takes the same SRE workspace lock and rejects re-intake of the same project/video/content SHA under the revoked policy, and for `privacy_delete/source_deleted` also across a different policy revision. Thus deleting the original S3 row cannot silently resurrect identical content under a new ID.

**Strict boundaries:** This is a documented **primary-PostgreSQL logical row removal**, not a guaranteed secure disk overwrite, WAL/log/backup erasure, D1 origin deletion, processor/provider copy removal or evidence-free deletion of paid M26–M33 work. LIVE-pinned source S3 cannot be removed by this port. A rights-only revocation does not authorize source-row deletion. No automatic deletion is coupled to M34 tombstone; the extra host permission must be granted explicitly. M34 production/full-physical DoD remains [ ] BLOCKED.

**Auditable 20 counters:** `audit_sre_source_revocation_remnants` now independently counts persistent original S3 primary row, immutable primary-row removal certificate, active LIVE runs still missing an immediate stop and S4 runs still active, in addition to the 16 prior source/finance/data counters. It does not treat an empty JSONB source payload as proof of deletion. `primary_s3_row_absent_with_certificate=true` proves only a verified absent original row with a certificate, not secure physical/media erasure. Any missing active-run stop appears in the protection-violation list.

**QA authored, not verified green:** PG17 tests cover same-discovery re-intake refusal after S3 row deletion, direct pre-M15 outbox-ACK forgery, same-transaction LIVE cancel flag, SQL reactivation rejection, queued S4 cancellation, source-row deletion for real S4-only D1 revisions, malicious certificate denial, immutable certificate replay, and denial of primary S3 deletion for LIVE-pinned data. Unit and schema tests cover reason/role/FK/certificate and 20-counter residual audit. No real paid Opus request, model inference, or cross-owner export deletion.

## M34 continuation — S4 completed-run invalidation and migration regression repair

An already `completed` offline-fixture S4 run may lose its original synthetic labels, evidence, input contexts and stage executions when one source is revoked. Its historic parent classification and S4 run statuses cannot still advertise successful completion. Forward-only 068 now sets **both** `sre_offline_runs` and `sre_classification_runs` to `cancelled` on the first tombstone, even if they were formerly completed, and records `cancel_requested=TRUE`. An additional `BEFORE UPDATE` guard on the S4 parent classification table prevents a late worker or direct SQL writer from switching it back to completed/running. Immutable lineage IDs and original finance evidence remain intact.

The M34 schema-regression file had become syntactically corrupted by a repeated text insertion, and the tracking history contained a duplicated body. No success is claimed until the repaired tests and PostgreSQL17 fixture have run on the exact same HEAD.

## M34 continuation — financial hold freeze/release correctness

**Source withdrawal must never fabricate a refund.** A new atomic SQL action inside the existing 068 tombstone AFTER INSERT trigger releases a reserved M25 budget **only if there is no recorded M26 committed dispatch intent and no paid/UNKNOWN M15 attempt witness**. The existing M25 one-way `reserved → released` trigger validates the same safety rule, updates NUMERIC(24,9) account balances and appends an immutable `released` budget event; paid/unknown/resolved `settled` records are left intact. This is not a charge reversal. Replaying the tombstone does not release twice, because the action runs only on first insert. **M34 SQL rejects new M24 paid consent and M25 reservation INSERT** for the source even if a previous quote exists. M34 also revokes **unused, unsent M24 human approvals** using the existing strictly one-way `security_revoked` audit fields; any original consent attached to a M26 committed intent or potentially paid M15 witness remains intact as historical proof.

The authorized, READ ONLY `audit_sre_source_revocation_remnants` includes **20 exact per-source counters** and separates `unrevoked_pre_dispatch_consents` (must be zero after revocation), `releasable_pre_dispatch_holds` (must be zero after tombstone; a nonzero value is a protection failure) from `protected_paid_or_unknown_holds` (an allowed outstanding financial liability, never silently released). It retains source-level counted M28 provider receipts and never suggests physical deletion of accounting records.

**Tests are authored, not PASSED:** `test_m34_pg_revoke_releases_only_pre_dispatch_M25_hold` uses real C9+D1/Opus quote/explicit consent/M25 hold (no network), verifies exact reserved=0, released=original amount, spent=0, one release journal event, no duplicate refund on replay, unused M24 consent revoked and preserved original quote. These are fixture cases, not evidence of real paid OpenRouter calls.

It verifies zero remaining M18 vectors, S4 contexts/results/stage executions and S3/LIVE readable views; separately reports historical S3 JSON payloads, immutable M23 quotes, M28 receipts, M30/M32/M33 evidence and pending cancellations. A nonzero disposable count raises `remaining_protective_invariant_violations`, not a false PASS. It never returns actual source/quote/model text.
- **Retention-expiry callback:** `record_expired_sre_content_revocations` scans S3 source timestamps and source-level retention via current PostgreSQL clock, with 1–100 versions per call. A new `sre_offline_revocation_fences` FK table retains the revoked (project, offline run, content version) identity after the S4 item is removed; SQL rejects late S4 stage INSERT/UPDATE and classification result INSERT/UPDATE even if an old worker wakes up after the cleanup.

## New forward-only schema 068

`intelligence/migrations/068_sre_live_source_revocation.sql`:

- `sre_live_source_tombstones`: permanent `(project_id,content_version_id)` primary key, original video/source-policy/sha256 pin, structured reason (`rights_revoked`, `source_deleted`, `retention_expired`, `privacy_delete`) and authorized actor. SQL INSERT checks exact existing original tenant-owned source row, project workspace synchronization; UPDATE/DELETE forbidden. No raw D1 title/content/transcript or free-form reason.
- AFTER INSERT cleanup atomically deletes exact SRE M18 embedding cache vectors and S4 offline-fixture item `contexts`, fake classification result/evidence rows and S4 stage-execution metadata; inserts one unique `sre_live_revocation_outbox` row per affected LIVE run. Any error rolls back all changes, so there is no half-committed tombstone/cache state. Historical paid receipts/reservations/intent/status records remain untouched.
- `sre_live_revocation_outbox`: project-content-run FK, fixed `pending` → `acknowledged` monotone state, original server timestamps and actor; trigger prohibits ACK while run is still active and not cancel-requested, forbids update after ACK and DELETE. Durable outbox can be retried after worker process failure; **no automatic paid retry**.
- S3 authoritative `sre_readable_content_versions` SQL view is replaced **in forward-only 068** with the unchanged old columns and all previous D1 dynamic policy/expiry/media requirements, plus `NOT EXISTS` original tombstone. SRE `sre_live_classification_results` projection similarly filters tombstones even if source policy is later re-enabled.
- BEFORE INSERT SQL guard blocks new SRE LIVE/offline item, OpenRouter quote, M24 paid consent, M25 reserve, M26 paid dispatch intent, M30 source-based result, M32 human review and M33 gold benchmark snapshot for tombstoned sources. Separate cache BEFORE INSERT guard prohibits vector regeneration. The permanent tombstone prevents data re-creation, not merely temporarily hides a record.

## Trusted internal service

`intelligence/relevance/live_source_revocation.py`:

- `record_sre_source_revocation(conn,project,content_version_id,*,expected_content_sha256,reason_code,actor_id,actor_authorizer)` requires `revoke_sre_source` host action and dedicated idle autocommit PostgreSQL connection. Acquires exclusive project workspace lock, checks **actual tenant-owned stored SHA and source-policy version**, writes idempotent tombstone, verifies all exact M18 cached vectors deleted. The first reason wins; a later replay cannot silently change provenance.
- `record_sre_source_policy_revocation(...)` requires that D1 policy/source is **already inactive or denied**; only then enumerates up to 1,000 project-owned SRE versions and invokes exact-idempotent callbacks. >1,000 is blocked rather than silently truncated. This is crash-replayable **per version**, not an atomic all-policy delete.
- `process_sre_source_revocation_outbox(...)` requires `process_sre_source_revocation`, calls the existing M15 `cancel_live_run` on safely cancellable LIVE runs, never attempts paid OpenRouter retries, and acknowledges only after SQL sees a cancellation flag/terminal state. A possibly charged `unknown` run with no cancel flag remains pending and is reported as requiring operator reconciliation. Crash leaves the outbox durable; repeated invocation is idempotent. **No background schedule automatically runs these callbacks.**
- `inspect_sre_source_revocation(...)` requires `read_sre_source_revocation`, is REPEATABLE READ READ ONLY, returns bounded counts/states/opaque run IDs, no source bytes. The flag is `source_text_exposed=false`, not `source_text_present=false`; original content may still be stored.
- `audit_sre_source_revocation_remnants(...)` returns privacy-minimal, independently counted disposable remnants, readable-view leakage counts and historical retained original/financial witness counts; never treats hiding as physical deletion.
- `record_expired_sre_content_revocations(...)` requires deliberate trusted invocation to sweep genuinely expired source revisions; no scheduled task exists.
- `intelligence/relevance/intake.py::read_content` and `intelligence/relevance/live_diagnostics.py` reject permanent tombstones; M32/M33 repeat rights via existing D1 read gate. The S3 SQL readable view and result projection also suppress revoked content.
