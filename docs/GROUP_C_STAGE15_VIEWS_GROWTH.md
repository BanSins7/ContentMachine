## Зачем нужен показатель

Скорость роста показывает, сколько **новых просмотров в час** публикация получила между двумя зафиксированными наблюдениями. Используется только проверенное время наблюдения \`observed_at\`, а не дата загрузки, \`collected_at\` или текущее системное время:

\`\`\`text
Прирост просмотров = views_current - views_previous
Точный интервал (микросекунды) =
  observed_at_current - observed_at_previous
Просмотров за час = Прирост просмотров × 3 600 000 000 /
                    Интервал в микросекундах
\`\`\`

Золотой вектор: 100 → 200 просмотров за 4 часа = **25.000000000000 просмотров/час**. С точностью до 1 микросекунды изменение на 1 просмотр = **3600000000.000000000000 просмотров/час**, если результат помещается в PostgreSQL NUMERIC(30,12). Проверены и значения меньше единицы (например, один просмотр за три часа → 0.333333333333).

Для времени используется тип \`datetime\` с явной timezone; оба момента нормализуются в UTC. Длительность вычисляется по целым дням, секундам и микросекундам объекта \`timedelta\` без \`float total_seconds()\`, округление результата — \`Decimal ROUND_HALF_UP\` до 12 знаков, переполнение \`NUMERIC(30,12)\` блокируется.

## Смысл отрицательных коррекций

Падение счётчика (например, 200 → 180) нельзя изображать как нулевой рост. Это **невалидное наблюдение для скоростного показателя**: \`ContractError(code='counter_decreased')\`, без усечения, \`ABS\`, подмены отрицательного прироста нулём или расчёта Breakout из исправленного счётчика. Исторические сырые значения остаются нетронутыми. Другие условия отказа: отсутствуют views, float/bool вместо BIGINT, два одинаковых снимка или одинаковый/обратный timestamp, неподтверждённая точность, некорректная версия метрики или источник.

## Разделение проверки и вычисления

- \`compute_views_growth_per_hour(previous_views, current_views, previous_observed_at, current_observed_at)\` — чистая точная функция; не читает БД, не отправляет ACK и не создаёт score.
- \`compute_verified_views_growth(C0Pair)\` — проверяет идентичность источника/версии, время и счётчики через существующий \`validate_c0_pair(require_score_fields=False)\`. Она не даёт разрешение на publication/scoring сама по себе.
- \`PostgreSQLViewsGrowth.derive(...)\` — единая проверка read-only источника через \`read_c0_pair(require_score_fields=False)\`: каноническое членство видео в проекте, проверенная metadata ID, источник/его current права и TTL, обе сырые записи с точным video ID / policy revision / metric definition+version, отсутствие assumed/corrected/retracted/partial observations, а также **точно два самых последних сырых снимка** для видео и источника, включая новую отозванную запись. Никакого возврата к старой «хорошей» паре.
- Изменение \`read_c0_pair\` обратно совместимо: новый параметр \`require_score_fields: bool=True\` по умолчанию сохраняет прежнюю строгую проверку всех необходимых для rates полей. Только скорость роста явно передаёт \`False\`, чтобы рассчитываться при известных views даже когда likes/comments/shares ещё NULL. При необходимости нулевые просмотры остаются валидным фактом для скорости, **но не для engagement-rate или Breakout**, где требуется положительный знаменатель.
- Отсутствие правообладателя, запрет хранить/выводить метрики, подмена snapshot ID, source policy/version, включение нового наблюдения, устаревшие retention факты или конфликт интервала блокируют чтение; не используются внешние API и неподтверждённые источники.

## Выход и граница одобрения

\`ViewsGrowthResult\` — immutable dataclass с точными project/video/source/policy/metric ID, metadata ID, двумя snapshot ID, обеими временными метками, первоначальными счётчиками, приростом просмотров, точной длительностью в микросекундах, Decimal скоростью и canonical SHA-256 всех полей-источников. Статус **\`growth_derived_unapproved\`**, \`ready_for_breakout=False\`: результат пригоден для дальнейшей проверенной сборки аналитики, но **не** выдаётся как одобренный итоговый Breakout Score.

Текущий этап не добавляет подпись рецензента и не проводит activation review на момент вычисления — это **не заявленное** одобрение от Group C. Следующие этапы 16–21 должны проверить цепочку human review, activation, frozen cohort и актуальные права повторно перед изменением статуса полного результата. Результаты роста не сохраняются в \`calculated_metrics\`, не меняют QDP, не публикуют Analytics outbox.
